今日学习记录：ECC 纠错复盘与 C++ 文件统计实验

发表于2026-08-01|更新于2026-08-01|科研学习
|阅读量:

今天整理的是 2026-08-01 两组已经完成并写入笔记的学习内容：一组来自数字水印方向，聚焦 ECC、有效载荷与最小水印链路诊断；另一组来自 C++ 基础训练，聚焦 std::vector、文件流、错误处理，以及 -O0/-O2 的端到端测量。这里仅记录当天已经在笔记、测试或实验结果中出现的内容，不补写尚未完成的成果。

今天实际确认了什么

先给出当天最重要的几个判断：

  • ECC 通过增加冗余换取纠错能力，但不会增加物理嵌入容量。
  • 相同的 Raw BER 不一定对应相同的解码结果，错误分布会直接影响纠错是否成功。
  • 当前最小水印链路已经接入 ECC，但这次诊断中解码前 Raw BER 为 0，因此不能把结果写成“ECC 把非零 BER 降为 0”。
  • 在 C++ 练习里，const 引用、输出参数与标准错误/退出码的区分，都是把程序从“能跑”推进到“可诊断”的关键。
  • 在当前机器、当前编译器和当前输入下，-O2 相比 -O0 的端到端文件统计中位时间更低，但这个结果只说明本次测量环境下的观察，不能泛化成所有程序都同比例提速。

解码方式是 Majority Vote（多数表决）。如果某组三个 bit 里最多只有 1 个错误，就还能恢复；如果同组出现 2 个或 3 个错误，就会失败。

因此，若物理嵌入容量是 300 bit，三重复码最多只携带 100 个有效信息 bit。当天学习里一个重要收获，就是把“物理嵌入容量”“编码后 payload”“有效 payload”严格区分开，避免把编码后的总 bit 数误写成真实信息量。

三类结果指标不能混写

当天笔记明确区分了三个指标：

  • Raw BER：纠错前码字比特错误率。
  • Decoded BER：纠错后消息比特错误率。
  • Message Success Rate：整条消息一位不差恢复的样本比例。

这组区分很重要，因为即使 Raw BER 一样，错误是否集中在同一个重复组里，也可能让最终纠错结果完全不同。只报告平均 Raw BER，可能会掩盖 ECC 是否真正改善了解码结果。

C++ 容器、文件流与 -O0/-O2 测量

当天补清楚的几个基础概念

这一部分记录的是 C++ 基础训练里当天真正确认下来的内容：

  • std::vector 是可动态增长的顺序容器。
  • const std::vector<int>& 适合只读的大容器参数，避免复制且禁止通过该引用修改原容器。
  • std::vector<int>& 直接引用原容器，允许函数原地修改调用者数据。
  • .at() 会做边界检查并在越界时抛出 std::out_of_range，[] 不保证做同样的保护。
  • std::ifstream 与 std::getline 适合实现基础文件读取；而 stdout、stderr 与退出码需要分开设计，才能让错误被正确诊断。

当日笔记还特别强调了一个接口设计点：函数可以同时返回“是否成功”和“统计结果”。例如让 bool 表示成功或失败，再通过 FileStats& 写回行数和词数，比把错误情况伪装成 0/0 更清晰。

当天实际做过的实验

公开可确认的工作包括：

  • 在 Windows 本机确认使用 MSYS2 UCRT64 g++ 14.2.0，将实验环境从 Codespaces 切到本地。
  • 编译运行 vector_demo.cpp，验证只读引用、原地修改和 .at() 越界异常捕获。
  • 实现 file_stats.cpp，统计行数与词数，并区分成功、空文件、缺失文件和参数错误。
  • 使用 cmd 原始重定向确认：缺失文件时 stdout 为 0 字节，错误信息写入 stderr，退出码为 1。
  • 对同一份源码分别编译 -O0 与 -O2 版本，在 500,000 行输入上各预热 2 次、测量 5 次。

这里真正有价值的，不只是“跑出了一个时间表”，而是把测量的公平性条件收紧到只改变一个变量：优化级别。

当前测量结果

当天笔记中的端到端测量结果如下：

编译级别 5 次时间（ms） 中位数
-O0 202.22、190.77、189.85、186.17、158.61 189.85
-O2 140.24、143.40、153.85、166.55、140.54 143.40

据此可得出的当天观察是：

  • 在固定环境下，-O2 的中位数比 -O0 少 46.45 ms。
  • 这相当于约 24.5% 的下降，或约 1.32× 的速度比。

但同样需要保留边界：这只能证明当前机器、当前 G++、当前源码和当前输入条件下的端到端表现，不能直接推出某个具体优化 pass 的贡献，也不能外推到所有程序。

一个实际失败案例：Windows DLL 启动失败

这部分笔记还记录了一个很典型的本地环境问题：

  • 症状：vector_demo.exe 编译成功，但运行时无输出退出，状态为 -1073741511（0xC0000139）。
  • 记录下来的根因：MSYS2 UCRT64 与 Anaconda MinGW 同时存在同名 GCC 运行时 DLL，存在搜索优先级兼容性冲突风险。
  • 当天采取的修复：在当前终端前置 UCRT64 路径，即执行 $env:PATH = "E:\c++\ucrt64\bin;$env:PATH"。
  • 验证结果：同一程序恢复正常输出，退出码为 0。

这条记录的价值在于把“程序跑不起来”从模糊现象收敛成了可复现、可修复、可验证的问题单，而不是简单记成“环境出了点问题”。

今天还没完成什么

按原始笔记，当前仍有几项明确未完成内容：

  • C++ 方向还缺 60 分钟独立文件统计 B 门，以及不同故障版本的独立 T 门。
  • 数学维度正式 20 题、90% 考核尚未完成。
  • 数字水印方向还没有在多图、多条件下验证真实攻击场景里的 ECC 收益。

因此，今天更适合把结论写成“基础概念和最小链路进一步收紧”，而不是把它扩写成“已经完成鲁棒性证明”或“已经掌握完整训练能力”。

明天的衔接点

原始笔记里已经给出了下一步方向：

  • 数字水印学习进入第一周概念复习与缺口检查。
