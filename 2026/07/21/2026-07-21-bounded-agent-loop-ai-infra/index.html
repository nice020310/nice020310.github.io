多媒体取证 Agent 学习笔记：Bounded Agent 闭环与 AI Infra 约束

发表于2026-07-21|更新于2026-07-21|多媒体取证 Agent
|阅读量:

今天整理的是 Day 6 的核心收获：继续保留外层确定性的 RAG Workflow，只把“多步工具选择”收进一个有预算、有白名单、可审计的 Bounded Agent 闭环里。同时，这一天还系统补上了与这套设计直接相关的工程约束，包括 GPU 推理链路、Redis checkpoint、RabbitMQ 异步恢复，以及 JWT 场景下的工具授权边界。

这次学习的重点不是把系统包装成“已经完成的通用自主 Agent”，而是明确一个更稳妥的落地方向：动态能力可以有，但必须被 Workflow、预算和权限边界约束住。

这次升级真正解决什么问题

到 Day 5 为止，系统已经有受约束的工具层，但工具选择本身还是固定映射，更像 Tool-Enabled Workflow，而不是能根据中间结果动态决策的执行闭环。

问题在于，一旦任务不再是“固定问题对应固定工具”，就会出现两个工程风险：

  • 全部继续写死，系统缺少根据证据结果切换动作的能力。
  • 全部交给开放式 Agent，自由度上去了，但可预测性、可测试性和可审计性明显下降。

Day 6 的目标，就是在这两者之间找到一个受控中间态：让 Planner 能基于 goal + observations 动态选择动作，但整个闭环依然受外层 Workflow、白名单工具、轮次预算、时间预算和验证节点控制。

这意味着当前系统依然不是自由 Agent，而是 Workflow-Orchestrated Bounded Agent。它的动态性来自内层闭环，但系统主边界仍由外层状态机守住。

这次学习把 Agent 最小闭环明确成：

其中最重要的不是动作数量，而是 observation 的作用。它不只是执行日志，而是下一轮决策的输入：Planner 会读取当前 goal、允许的工具集合，以及历史 observations，决定下一步是继续摘要、提取指标、登记报告，还是直接结束。

但 observation 也被严格约束。系统只保留结构化摘要、状态和 citation IDs，不保存完整 PDF、完整 prompt 或敏感凭证到 trace。这样做是为了避免短期 memory 失控膨胀，也避免把敏感信息带进可持久化调试链路。

这次把哪些边界真正工程化了

Day 6 一个很大的进展，是把“受约束 Agent”从概念变成了可执行规则。

1. 工具白名单和结构化动作

Planner 只允许选择三类工具：

  • summarize_paper
  • extract_metrics
  • generate_report

而且 Planner 不允许直接提供任意路径、任意参数或函数名，只能输出结构化动作，例如：

具体 payload 由服务端根据可信状态构造。这样做的价值很直接：模型只能表达“意图”，不能越权决定“怎么调、调什么参数、访问哪个路径”。

2. 预算上限

这次把三类预算都明确了：

  • 最多 3 次真实工具调用
  • 最多 5 轮 Planner 决策
  • 总 deadline 20 秒

它们限制的是不同风险：工具调用限制外部成本和副作用，Planner 轮次限制空转和非法重复决策，deadline 限制整段执行的墙钟时间。三者不能相互替代。

3. 重复动作检测

系统为动作建立 signature，避免同一工具对同一输入重复执行。

  • 对已经成功的相同动作，直接复用 observation，不再再次调用。
  • 对已经失败的相同动作，阻断连续重试，要求 Planner 选择替代动作或结束。

这一步非常关键。否则 Planner 很容易在局部失败后陷入“重复同一个动作 hoping it works”的死循环。

4. 报告工具后置

generate_report 依然不能绕过 Verify。即使 Planner 选择了报告动作，系统也只把它登记为 pending_post_verify_tool，在 Verify 完成前结束 Agent 循环，等校验通过后才真正执行报告生成。

这和 Day 5 的原则是一致的：报告一旦落盘，就属于持久化副作用，因此只能消费已经通过验证的答案与引用，不能提前执行。

这次学习里的 AI Infra，不是旁支，而是 Agent 约束的现实依据

这一天新增的 AI Infra 内容，和 Bounded Agent 不是两条平行线，而是同一个工程问题的两面。

同时也明确了关键指标：

  • TTFT
  • TPOT
  • tokens/s
  • P95 / P99
  • queue wait
  • OOM

对单轮问答来说，这些指标已经重要；对 Agent 来说更重要，因为每多一轮 Planner、每多一次工具后续推理，都会放大 token 成本、尾延迟和故障概率。也正因为如此，Day 6 才会强调 Agent 不能无限循环，必须把动态能力放进预算盒子里。

GPU 调度理解为什么要进入项目复述

这一天也系统复盘了 GPU 显存和调度基础：

  • 显存由模型权重、KV cache、激活和临时工作区组成。
  • prefill 偏计算密集，decode 偏内存带宽。
  • batch 提高吞吐，但会增加显存压力、排队时间和尾延迟。
  • 真实调度要考虑队列、配额、优先级、bin packing、抢占和多租户隔离。

这里最重要的不是“我已经做了 GPU 调度平台”，而是要准确表述真实性边界：当前只是完成概念理解和项目映射，没有实现真实生产级 GPU 调度系统。

Redis、RabbitMQ 和 JWT 为什么正好在这一天补上

因为一旦系统进入“多步动作 + 可能中断 + 可能重试 + 可能异步执行”的阶段，就必须考虑恢复、幂等和授权边界。

Redis：Checkpoint 只负责短期恢复

这次学习里给出了明确的 checkpoint 设计：

保存内容包括 round、status、observations 摘要、已使用 signatures、deadline 和 version，并结合 TTL 与 version + Lua/CAS 避免并发覆盖。

但边界也讲得很清楚：Redis 只适合做短期恢复和排障，不适合作为长期真相源。完整 prompt、PDF 正文和 JWT 也不能写进去。

RabbitMQ：异步报告必须把幂等和恢复做全

这次整理的关键点包括：

  • API 创建 task 与 outbox 事件
  • 使用 publisher confirm、durable queue/message、manual ACK
  • 以 task_id 或 idempotency key 保证任务幂等
  • ACK 丢失重投时返回已有结果，而不是重复生成
  • 失败消息有限重试后进入 DLQ

这些内容和 Bounded Agent 是直接相连的：如果工具链将来进入异步执行，恢复逻辑必须知道哪些动作已经做过、哪些副作用必须幂等、哪些结果可以复用。

JWT：合法 Token 不等于有权调所有工具

这一天对授权边界的总结也很到位：

  • Authentication 解决“你是谁”
  • Authorization 解决“你能对什么资源做什么”

在工具调用场景下，真正可信的权限来源只能是服务端构造的 ExecutionContext，而不是 prompt 或 observation 里自称的身份。系统需要校验 tenant、资源归属、tool permission、配额，以及异步 Worker 场景下的重新授权，避免 IDOR 或越权调用。

这次最值得保留的项目话术

如果要用一段话总结 Day 6，我会这样说：

我保留了外层确定性的 RAG Workflow，只把多步工具选择放进一个 bounded agent loop。Planner 会根据 goal 和 observations 动态选择摘要、指标或报告工具，但受到白名单、最多三次工具调用、五轮规划、20 秒 deadline、重复动作检测和 Verify 节点约束。系统因此具备 Plan-Act-Observe-Replan 的闭环能力，但仍然是可测试、可审计、可降级的 Workflow-Orchestrated Bounded Agent，而不是开放式自由 Agent。

这段话的价值在于，它既说明了这次确实补上了动态能力，也没有把尚未完成的长期 memory、多 Agent、分布式 runtime 或真实 GPU 调度平台讲成已经落地的成果。

Day 6 完成了什么，也明确没完成什么

从当天学习记录看，已经完成和固定下来的内容包括：

  • 在现有 Workflow 内加入 Bounded Agent 闭环
  • 增加结构化动作、工具白名单和服务端 payload builder
  • 加入动作去重、预算终止、失败回退和报告后置
  • 补齐相关测试，记录为 47 passed
  • 完成 AI Infra、Redis checkpoint、RabbitMQ 异步恢复、JWT Tool 授权的项目化学习整理

同时也明确保留了边界：

  • 还没有真实长期 memory
  • 还没有多 Agent 协作
  • 还没有生产级分布式 Agent Runtime
  • 还没有真实 DeepSeek Planner 质量验证
  • 还没有真实 Redis、RabbitMQ、GPU 环境下的生产演示

这类边界表述并不是“保守”，而是工程上必要的准确性。系统真正可信，不只是因为它做了什么，还因为它明确知道自己还没做什么。
