多媒体取证 Agent 学习笔记：Day 1 从现有 RAG 到 Agentic Workflow 设计

发表于2026-07-16|更新于2026-07-19|AI
|阅读量:

这一天没有急着改代码，而是先把当前项目链路、目标架构和升级边界全部重新梳理了一遍。对这个多媒体取证论文问答项目来说，这一步很必要，因为如果连现有系统的能力边界都说不清，后面的 Hybrid Retrieval、Rerank 和 Workflow 只会变成堆功能。

当前系统到底做到哪一步

先把已经跑通的链路固定下来：

这个版本已经能完成最基础的论文问答，但还不能叫完整的 Agent 系统。原因也很直接：

  • 只有单路 Dense Top-K 检索
  • 没有显式相关性门控
  • 没有多路召回和精排
  • 没有可审计的 Workflow 状态
  • 当前所谓 Agent 更接近规则驱动函数，而不是 LLM 驱动的工具决策循环

这一步最大的价值，是把“已经实现”和“计划实现”分开，避免后面在项目表达里把设计稿说成现网能力。

为什么先去看 Dify

我这一天专门做了一个最小 Dify Workflow 实验，不是为了把项目迁移到 Dify，而是为了借它的抽象把自己的系统重新看一遍。

实验链路很简单：

这个实验让我更明确了几个概念：

  • Workflow 的核心不是可视化，而是节点输入输出、失败策略和状态传递都可控
  • RAG Pipeline 应拆成离线索引和在线问答两部分
  • Agent 适合路径不确定、需要动态工具选择的任务
  • 论文问答主链路更适合 Workflow，而不是把每一步都交给 Agent 自由规划

最小实验暴露了什么问题

在 Dify 里跑最小 Workflow 后，几个问题非常明显。

第一，Dense Top-K 会强制返回“最相似”的片段，但“最相似”并不等于“真正相关”。例如问为什么选择 Chroma 而不是 FAISS 时，系统可能召回和 embedding 模型有关的片段，而不是向量库选型本身。

第二，复合问题会把多个意图压成一个 query，单次检索经常只能覆盖一部分子问题。

第三，拒答如果只靠 Prompt 驱动，稳定性很差。系统需要显式的相关性门控，而不是只依赖模型“看起来比较谨慎”。

第四，“没有证据”和“证据表明没有实现”不是一回事。对后者，系统不该一律说“证据不足”，而应该能回答“当前没有使用”。

这些观察，直接决定了后面几天的主线不是继续加大模型，而是依次补上：

  • Hybrid Retrieval
  • Cross-Encoder Rerank
  • Relevance Gate
  • Query Decomposition
  • Coverage Verify

Day 1 最重要的输出

这一天最关键的成果不是代码，而是把目标架构说清楚了。

后续 Workflow 的核心节点被固定为：

节点 作用
Query Analyzer 规范化问题、识别任务类型、拆分子问题
Hybrid Retriever 用 BM25 和 Dense 做多路召回
RRF Fusion 用排名做无量纲融合
Reranker 对候选证据做精细语义排序
Relevance Gate 证据不足时在生成前拒答
Answer Verifier 检查引用支持和子问题覆盖情况

配套状态字段也先约定了出来，例如 request_id、question、task_type、sources、answer、confidence 和 trace。这一步的意义是让后续每次升级都落在明确节点上，而不是继续在单个 RagEngine 里堆逻辑。

这一天没有做什么

为了避免把路线越拉越散，这一天也明确了边界：

  • 没有把设计稿描述成已实现功能
  • 没有提前引入多 Agent
  • 没有写业务代码去“抢进度”
  • 没有为了追求功能数忽略链路可解释性

这其实比新增几个模块更重要，因为后面每一层优化都要能回答两个问题：为什么存在，失败后怎么办。

一个更准确的总结

如果要用一句话概括 Day 1，我会这样表述：

我先把已有论文问答系统的真实能力边界重新厘清，并通过 Dify 最小 Workflow 实验验证了当前单路 Dense RAG 的典型问题，包括错误召回、复合问题漏覆盖和 Prompt 式拒答不稳定。基于这些观察，我把后续升级主链路固定为 Hybrid Retrieval、Rerank、Gate、Generate 和 Verify 组成的可控 Workflow，而不是继续把主系统做成黑盒式的单函数调用。

Day 1 的价值，不是“多做了什么功能”，而是把后面几天的技术升级路线真正定准了。
