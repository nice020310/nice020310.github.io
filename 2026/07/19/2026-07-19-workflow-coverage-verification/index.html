多媒体取证 Agent 学习笔记：Day 4 把串行 RagEngine 拆成显式 Workflow

发表于2026-07-19|更新于2026-07-19|AI
|阅读量:

前面三天已经把召回、精排和拒答这些关键模块补起来了，但系统主链路依然偏串行：拿到一个问题后，在一个大函数里依次完成检索、生成和返回。

Day 4 的核心任务，就是把这条链路拆成显式 Workflow，并且让复合问题场景拥有更清晰的覆盖率语义。

这次想解决的真实问题

如果用户一次问两个子问题，而系统只找到了其中一个的证据，原来的串行链路通常只有两种不理想的结果：

  • 整体失败，明明有一半内容能可靠回答
  • 整体作答，把没证据的那一半也顺手编出来

Day 4 要解决的，就是这种“部分可答但边界不清”的情况。

和前几天相比，最关键的变化有两个：

第一，问题会先被拆成子问题，再分别走检索、精排和门控。

第二，最终状态不再只看模型有没有生成文本，而是看每个子问题是否真的有证据支持、是否带了合法引用，以及整体 coverage 到底是多少。

意义不在于字段多，而在于后续每个节点都只能读取和更新约定字段。这样 Workflow 才是可测试、可回放、可解释的状态机，而不是继续在一个大函数里靠隐式变量把所有逻辑串起来。

这次拆出的六个核心节点

Day 4 明确了六个节点的输入、输出和失败策略：

节点 输入 输出 失败策略
QueryAnalyzer question task_type、normalized_query、sub_queries、filters 回退为单个原问题
RetrieveNode sub_queries 每个子问题的 sources/status/confidence 单子问题拒答或降级，不中断其他子问题
MergeNode subquery results chunk_id 去重后的 sources、sub_query_hits 保留有效路线
GenerateNode supported subqueries + sources answer_parts + citation chunk_ids JSON 失败有限修复一次
VerifyNode answer_parts + sources coverage、missing、invalid citations 删除无效引用，部分或整体拒答
FormatNode state 兼容旧 API 的最终响应 保留已有 answer/sources 字段

这张表真正把“节点为什么存在”和“失败后怎么办”都提前说清楚了。很多系统不稳定，不是因为模型不够强，而是因为失败策略根本没被工程化定义。

这一天完成的关键实现

从笔记记录看，Day 4 已经明确完成或固定下来的设计包括：

  • 新增轻量 typed Workflow，不额外引入 LangGraph
  • Query Analyzer 默认走结构化 JSON，失败时回退原问题
  • 每个 sub_query 继续复用已有 Hybrid -> Rerank -> Gate
  • 按 chunk_id 合并证据，并记录每个 chunk 支持哪些子问题
  • Generator 输出结构化 answer_parts，每段附带 citation chunk IDs
  • Verifier 自动检查引用是否合法，并重新计算 coverage
  • /api/papers/ask 在兼容旧字段的前提下，补充 request_id、task_type、sub_queries、coverage 和 missing_sub_questions

这里最重要的一点，是把“回答生成”和“回答可采信”分开。生成阶段可以先给出结构化答案，但最终是否算回答成功，要看验证阶段的引用检查和覆盖率判断。

这次测试关注的不是单个样例效果

Day 4 的测试设计明显比前几天更偏行为验证：

  • 单问题退化为一个 sub_query
  • 复合问题拆成多个 sub_queries
  • 多个子问题命中同一证据时按 chunk_id 去重
  • coverage=2/2 返回 answered
  • coverage=1/2 返回 partial
  • coverage=0/2 不调用 Generator，直接 refused
  • 非法 citation 会被删除并降低 coverage
  • 某一路 degraded 不影响其他子问题完成

这说明关注点已经从“模型答得像不像”转向“系统对边界情况是否有稳定且可解释的处理方式”。

Day 4 明确没有做什么

这一天也专门划清了边界，没有把下面这些内容算进已完成：

  • Agent Tool Selection
  • 多 Agent 协作
  • 持久化索引
  • 完整 trace 与监控
  • 语义级 claim entailment

这很重要。因为 Day 4 的任务不是把所有概念一次性塞进系统，而是先把主问答链路真正做成 Workflow。

一个更准确的总结

如果要概括 Day 4，我会这样说：

我把原来的串行 RagEngine 拆成了显式 Workflow。系统先把复合问题拆成子问题，每个子问题独立执行 Hybrid Retrieval、Rerank 和 Gate，再按 chunk_id 合并证据，生成带 citation ID 的分项答案，最后通过 Verifier 检查引用合法性并计算 coverage。这样系统可以对缺失子问题做部分拒答，而不是因为一部分没证据就整体失败，或者直接编造答案。

Day 4 的核心意义，不是“多了几个节点”，而是把复合问题问答从一条隐式串行调用链，推进成了一条边界清晰、失败可解释、状态可观察的 Workflow。
