多媒体取证 Agent 学习笔记：把串行 RAG 拆成可验证 Workflow

发表于2026-07-19|更新于2026-07-19|AI
|阅读量:

今天的学习重点，不是再往系统里堆一个新能力，而是把原先串行的 RagEngine 主链路拆成显式 Workflow，让复杂问题问答具备更清晰的状态语义、失败边界和可验证性。

为什么要从串行链路升级到 Workflow

原先链路的问题不在于“不能回答”，而在于一旦碰到复合问题，系统很难准确表达“哪些子问题有证据、哪些子问题没有证据”。

典型场景是：用户一次提两个子问题，但系统只找到了其中一个的证据。这个时候如果整体拒答，会浪费掉已经检索到的有效信息；如果整体作答，又容易把没有证据支撑的部分一并编出来。

这次改造的目标，就是把这种“部分可答”的情况工程化表达出来。

  1. 先把复合问题拆成多个 sub_queries，每个子问题独立走检索、精排和门控。
  2. 最终状态不再只看“模型有没有输出一段像样的话”，而是看每个子问题是否真的有证据支持、引用是否合法，以及整体 coverage 到底是多少。

这样做的意义，不是字段越多越好，而是把节点之间的数据契约定清楚。后续每个节点只读写约定字段，避免继续依赖大函数里的隐式共享变量。

显式 WorkflowState 带来的直接收益是：

  • 节点职责更清晰，便于单测和回放。
  • 失败边界可以局部处理，不必一处异常拖垮整条链路。
  • 最终结果可以解释“为什么是 partial / refused / degraded”。

六个核心节点分别解决什么问题

节点 作用 失败时怎么处理
QueryAnalyzer 规范化问题、识别 task_type、拆分 sub_queries 分析失败时回退为原问题单子查询
RetrieveNode 每个子问题独立执行 Hybrid Retrieval 单个子问题失败不影响其他子问题继续
MergeNode 按 chunk_id 去重并记录 sub_query_hits 保留已有有效证据
GenerateNode 生成结构化 answer_parts 并附带引用 chunk IDs 输出非法 JSON 时只做一次有限修复重试
VerifyNode 校验引用是否合法并重算 coverage 删除无效引用，必要时降级为 partial 或 refused
FormatNode 输出兼容现有 API 的最终响应 保留已存在的 answer/sources 契约

真正重要的不是“拆成了六步”，而是每一步都定义了输入、输出和失败后的具体动作。

今天补齐的关键实现和测试意识

从今天的复盘记录看，比较关键的落地点有这些：

  • QueryAnalyzer 先走结构化 JSON 分析，失败时回退到原问题单查询。
  • 每个 sub_query 继续复用已有的 Hybrid -> Rerank -> Gate 逻辑。
  • MergeNode 会按 chunk_id 合并证据，并记录一个证据块支撑了哪些子问题。
  • GenerateNode 输出的是带 citation_chunk_ids 的结构化答案片段，而不是直接吐最终自然语言。
  • VerifyNode 会检查引用是否真的属于对应子问题的召回结果，再决定 coverage 和最终状态。
  • 测试关注点开始从“模型答得像不像”转向“边界情况能否稳定处理”，比如 coverage=1/2 是否正确返回 partial、非法 citation 是否会被剔除、coverage=0 时是否直接短路不调用生成节点。

今天明确没有做的内容

这次学习里也专门划清了边界，以下内容不应被描述成“已经完成”：

  • Agent 级别的自主工具选择
  • 多 Agent 协作
  • 持久化索引迁移
  • 完整 trace / 监控体系
  • 更强语义级引用验证

也就是说，这次的重点是把主问答链路从“串行大函数”推进到“可解释、可验证、可局部降级的 Workflow”，而不是一次性把所有高级能力都塞进去。

一个更准确的总结

如果只用一句话概括今天的收获，那就是：

把原来串行执行的 RAG 主链路拆成了显式 Workflow，让复合问题能够先拆分、再分别检索和验证，最终根据真实证据覆盖率返回 answered、partial、degraded 或 refused，而不是一刀切地整体作答或整体失败。

这次改造最重要的工程价值，不是节点数变多，而是系统第一次能清楚说明：它为什么能答、答了多少、缺了什么，以及失败时是如何降级的。
