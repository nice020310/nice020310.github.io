Workflow 节点化实践：为复合问题问答增加 Coverage 验证

发表于2026-07-18|更新于2026-07-18|AI
|阅读量:

今天把原本偏串行的 RagEngine 进一步拆成了显式 Workflow，目标不是“让系统更聪明”，而是让复合问题场景里的行为更可解释、更稳定。

这次调整的核心是：把一个复杂问题拆成多个子问题，让每个子问题独立检索、独立校验，再根据证据覆盖情况决定最终回答状态，而不是在某一路缺证据时直接整体失败，或者更糟的是编造答案。

为什么要把主链路改成 Workflow

对于论文问答这类主链路任务，最重要的不是“自由决策”，而是：

  • 节点职责清晰
  • 状态字段显式
  • 失败路径可预测
  • 输出结果能解释为什么回答、部分回答或拒答

这也是 Workflow 和全 Agent 模式最本质的区别。

Workflow 适合固定、可审计、可回放的生产主链路；Agent 更适合工具选择高度动态、路径不稳定的任务。当前这个 Paper QA 场景，主干链路显然更适合前者。

节点契约与失败策略

今天明确了六个核心节点的输入、输出和失败策略：

节点 输入 输出 失败策略
QueryAnalyzer question task_type、normalized_query、sub_queries、filters 回退为单个原问题
RetrieveNode sub_queries 每个子问题的 sources/status/confidence 单子问题拒答或降级，不中断其他子问题
MergeNode subquery results chunk_id 去重后的 sources、sub_query_hits 保留有效路线
GenerateNode supported subqueries + sources answer_parts + citation chunk_ids JSON 失败时有限修复一次
VerifyNode answer_parts + sources coverage、missing、invalid citations 删除无效引用，部分或整体拒答
FormatNode state 兼容旧 API 的最终响应 保留已有 answer/sources 字段

这里最关键的不是拆节点本身，而是把“失败时怎么办”提前定义清楚。很多问答系统不稳定，不是因为检索或模型本身太差，而是因为失败路径没有工程化约束。

这次实现的关键点

今天已经落地的设计包括：

  • 新增轻量 typed Workflow，不额外引入 LangGraph，先避免 Python 3.8 兼容风险
  • Query Analyzer 默认走结构化 JSON 输出，解析失败时回退原问题
  • 每个 sub_query 仍然复用现有 Hybrid -> Rerank -> Gate 链路
  • 合并阶段按 chunk_id 去重，并记录每个证据片段支持哪些子问题
  • Generator 产出结构化 answer_parts，每段回答携带引用的 citation chunk IDs
  • Verifier 检查引用是否合法，并据此重新计算覆盖率

这套语义对复合问题非常重要。

如果用户一次问两个问题，而系统只能可靠回答其中一个，最合理的行为不是“硬凑一个完整答案”，也不是“一刀切全部拒绝”，而是返回 partial，明确缺失的是哪一部分。

为什么要加 Coverage Verify

今天最重要的一个收获，是把“回答生成”与“回答可采信”分开。

生成阶段可以先产出结构化回答，但真正决定结果状态的是验证阶段。只要 citation 指向不存在的 chunk_id，或者某个子问题没有被有效证据覆盖，这一部分就不能计入 coverage。

这带来的价值有两个：

  1. 能抑制“看起来答了，其实没证据”的假完成
  2. 能把部分失败显式暴露出来，而不是被一句流畅自然的总结掩盖

对于面向论文、知识库或检索增强问答的系统，这一步比继续堆模型能力更关键。

测试场景如何设计

今天为这条链路设计的测试思路，重点放在确定性和边界行为上，而不是单个样例的主观效果：

  • 单问题退化为一个 sub_query，保持旧行为
  • 复合问题拆成多个 sub_queries 并分别检索
  • 多个子问题命中同一证据时按 chunk_id 去重
  • coverage=2/2 返回 answered
  • coverage=1/2 返回 partial
  • coverage=0/2 不调用 Generator，直接 refused
  • Analyzer 失败时回退原问题
  • 非法 citation 会被 Verifier 删除并降低 coverage
  • 某一路 degraded 不影响其他已完成子问题

这类测试的目标不是证明系统“已经达到生产级”，而是证明它对复合问题的覆盖处理是可解释、可复现的。

今天的边界

今天没有把下面这些内容算进“已完成”：

  • Agent Tool Selection
  • 多 Agent 协作
  • 持久化索引
  • 完整 trace 与监控
  • 语义级 claim entailment

这几个方向都值得做，但它们不是今天这次节点化改造的完成标准。先把主链路的状态、节点契约和 coverage 语义打牢，比继续堆功能更重要。

一个更准确的总结

如果要用一句话概括今天的变化，可以这么说：

我把原来的串行 RagEngine 拆成显式 Workflow。Query Analyzer 先把复合问题拆成子问题，每个子问题独立执行检索、重排和门控；系统按 chunk_id 合并证据，Generator 生成带 citation ID 的分项答案，Verifier 再检查引用合法性并计算 coverage。这样系统可以对缺失子问题做部分拒答，而不是因为某一路缺证据就整体失败，或者直接编造答案。

这一步的意义，不只是“多加了几个节点”，而是把复合问题问答从“能跑”推进到“边界清楚、失败可解释、结果更可信”。
